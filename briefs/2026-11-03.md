# Agentic & AI interface brief — 2026-11-03

**Theme: Every layer assumes another one is checking.** MCP servers leave confirmation to hosts and most hosts don't ask. Harnesses close a command's input and count exit 0 as done. Compacted agents still have the rule in context and break it anyway. Agents sharing a repo build incompatible halves, and the human approver becomes the queue everything waits on. The harness job is to make the check happen in one place you can see, and to report what a step actually did, not just how it ended.

1. **[When Neither Side Confirms: Destructive Tool Approval Across MCP Servers and Hosts](https://arxiv.org/abs/2611.02527)** (arXiv 2611.02527), approval falls through the gap between server and host
   They read the source code on both sides. In a 1,000-repo sample of the official MCP registry, an estimated 90% of destructive tools have no server-side confirmation, and most servers that try to ask the user carry on, or fall back to a flag the model can set, when the host can't relay the question. Of 41 popular hosts and agent SDKs, 32 have no approval step by default. Pairing destructive tools with apps, 60.7% of pairs have no enforced human approval, and four of five cheap models ran an injected deletion in 479 of 960 runs. If hosts prompted for every tool not annotated read-only or non-destructive, the unapproved share would fall to 5.4%; universal support for servers asking the user would leave 56.7%. For your harness: the host owns approval. Treat unannotated tools as destructive by default, and never let a model-settable flag stand in for a person saying yes. Credibility: medium-high (source-code measurement with confidence intervals, five authors). Weight: high. Complements Nov 2's Caper (2610.40753): that's what to show the approver, this is making sure there is one.

2. **[RECEIPT: Measuring and Repairing the Return Assumption of LLM Agents in Web Service Operations](https://arxiv.org/abs/2611.01930)** (arXiv 2611.01930), exit 0 isn't "it happened"
   Many CLI commands ask a question before acting. If the harness closes input, the program can exit 0 without doing the thing; if it leaves a terminal open that nobody types into, the agent waits out a timeout. Of 158 checked invocations, 11.5% returned 0 without the requested action under closed input, and 7 of 8 tested harnesses close input when no terminal is attached. An unanswered prompt multiplied token use by 2.9, and fixing the input connection moved one model from 7th to 3rd of 8. RECEIPT keeps input open, reads from system calls what the process is waiting for, and tells the agent; false claims of success fell 73.5%. For your harness: detect "waiting for input" as its own tool-call state and show the actual question, and report what a call did, not just its exit code. Credibility: medium-high (91k production tool calls plus 89k public trajectories, six authors). Weight: high. Builds on Oct 30's honest tool-call states and Nov 2's evidence-guided recovery.

3. **[Do Agents Still Follow the Rules? Benchmarking Rule Compliance under Agent Context Compaction](https://arxiv.org/abs/2611.03223)** (arXiv 2611.03223), the rule survived, the obedience didn't
   ARCBench runs inside a real open-source harness (pi) and scores compliance from actions taken. Compaction rarely deletes the rule: most violations happen while the rule is still in the compacted history, with the agent reading a later request as permission. Runs that kept the rule still violated more than twice as often as runs with full history, and the strongest attack on the compactor more than doubled violations by corrupting the rule in the summary. For your harness: don't trust the summary to carry standing rules. Pin hard constraints outside compaction and enforce them in the harness, and show the user when a compaction happened and what it kept. Credibility: medium (four authors, one harness). Weight: medium-high. Complements Oct 26's Compact-Bench (2610.31710) and Oct 28's Context Is a Pipeline (2610.36114).

4. **[Getting a Grip: Operating Human-Agent Software Teams Through Governed Messages](https://arxiv.org/abs/2611.00689)** (arXiv 2611.00689), the human is the bottleneck, so design the queue
   yoars is a relay where people and agents from different vendors are authenticated principals exchanging typed, addressed messages in rooms that hold goals, decision rules, routing and an append-only record. In 926 controlled runs, changing which messages are allowed to start work (plus limits on repeated messages) cut coordination failure from 42% to 13%; instructed roles and votes didn't reliably work, and nothing inside the conversation stopped a planted backdoor. In a four-week field study with up to 19 agents and two people, requests waited mainly on the human coordinator and on approvals while agents answered within minutes, and holding context dominated token cost. For your harness: make "what can start work" and "what decision binds" explicit, attributable settings, and treat human approval throughput as the scarce resource to design around. Credibility: medium (pre-registered tests with honest adjusted p-values, field corpus released, candid about 26 failures of their own instruments). Weight: high for fleet design. Pairs with Nov 2's shared clarification queue (2610.41129).

5. **[Decentralized Multi-Agent Coordination and Communication in Shared Codebases](https://arxiv.org/abs/2611.00314)** (arXiv 2611.00314), parallel agents in one repo don't figure it out themselves
   ParallACT gives two agents separate requests in the same repo, some complementary and some contradictory. A single agent given both tasks solves most; parallel agents do much worse, and on contradictory pairs Claude Code with Opus 4.8 fell from 62% to 16%, with merged code usually satisfying only one spec. Telling an agent a peer exists didn't help much, and a communication channel recovered only a little at extra token cost. For your harness: detect overlapping or conflicting tasks before they run in parallel and route the conflict to a person or a single owner, rather than hoping agents negotiate. Credibility: medium (five authors, two harnesses and three open-weight models replicate the gap). Weight: medium-high.

6. **[Toward Bounding Coding-Agent Autonomy in Software Maintenance: A Pilot Study of Boundary Contracts](https://arxiv.org/abs/2611.01265)** (arXiv 2611.01265), mark what the agent may touch before it starts
   A Boundary Contract labels each artifact for a task as editable, inspect-only, required or protected before any edit. On 40 tasks from a real enterprise repo, the same Codex-based agent with contracts improved edit-selection F1 from 0.44 to 0.68 and doubled strictly acceptable patches from 9 to 18. For your harness: a pre-run scope view where the user or planner tags files with these roles is a concrete, non-chat control, and the same tags can be enforced at write time. Credibility: low-medium (the authors call it a pilot; 40 tasks, one repo). Weight: medium as interface design.

7. **[Claude Code v2.1.317](https://github.com/anthropics/claude-code/releases/tag/v2.1.317)**, plus [ACP RFD #2755: error classification](https://github.com/agentclientprotocol/agent-client-protocol/pull/2755), say what stopped and why
   Released Nov 2 (about 5:25 PM PT). Highlights:
   - Partial Grep and Glob results that hit a time limit are no longer treated as complete.
   - Auto mode now shows a notice when its check has no answer for a subagent's tool call, which used to show nothing.
   - The second of two simultaneous permission prompts no longer loses its file path or command on web and mobile.
   - `claude -p` now exits 1 when a full disk loses transcript writes, instead of 0.
   - Agent SDK hook callbacks can set `onFailure: "block"` so a failing check blocks the action.
   - A new warning appears when a cloud scheduled task gets connectors you didn't ask for, and a link card appears when an MCP server asks you to visit a link.

   ACP #2755 (draft RFD, opened this morning about 7:08 AM PT) proposes optional `kind`, `retryable` and `retryAfterMs` fields on turn-ending errors, so clients can tell a rate limit from an exhausted plan or a context overflow. For your harness: a failing safety check should block, not allow; partial results must say they're partial; and a stopped turn should show its cause and whether retrying could help. Credibility: high for the release notes (primary); the RFD is an open proposal only. Weight: medium.

**Takeaway for a non-chat+diff harness:** Own approval in the host and default unannotated tools to "ask". Show "waiting for input" and "partial" as real states. Enforce standing rules outside the context window. Catch conflicting parallel tasks before they run, and treat the human's approval queue as the system's scarcest resource.

# Agentic & AI interface brief — 2026-10-15

**Theme:** Supervise state, not turns. The task becomes a contract you can edit (desired / preserve / observed). An approval becomes a ledger record that a credential-holding adapter checks before it acts. A prompt is "accepted" when it is inserted, which is not the same as "done". A setting counts only if you can see the effective value. Wherever the user's only handle is a chat turn or a toggle they can't verify, the harness is asking for trust it hasn't earned.

1. **[Task-State Governance: TaskVM (arXiv 2610.20100)](https://arxiv.org/abs/2610.20100)**: edit the outcome contract, not the plan
   TaskVM represents a task as a desired / preserve / observed triad shown beside the live app. Edits compile into real GUI gestures, and completion has to be confirmed by an independent verifier that reads fresh screens, never by the executor's own report. Each action is labeled reversible, compensatable, or irreversible. The rollback preview marks effects that can't be auto-compensated, and epoch gating throws away stale proposals after a goal patch. Results: 21/36 strict contract passes vs 18/36 for Direct-CUA and 17/36 for Planner-CUA, at about 2.2× the wall time. In a 37-person within-subject replay study, recovery control rose +0.93 and trust +1.18 (both p<.01), and 11 participants used rollback 17 times vs 2 participants / 4 times on the chat baseline. Usable as a pattern for a coding harness: a "preserve" column (files, APIs, tests that must not change) checked by a separate verifier is a supervision object a diff view never gives you. Credibility: medium. A careful HCI paper that discloses its weak spots: a Wizard-of-Oz replay rig for the user study, one model for every role, a simulated app suite, and a self-selected Stage-3 group. Weight: high.

2. **[Guarded Commits: Transactional Human Approvals for LLM Workflows (arXiv 2610.00037)](https://arxiv.org/abs/2610.00037)**: approval is workflow state, and only the adapter holds the merge token
   The paper (MPI-SWS / MIT / Purdue) turns every approval into an append-only ledger record. The record binds the artifact hash (an EDIT binds pre / delta / post hashes), the pinned policy version and ledger prefix, and an executed-path witness showing that the path actually crossed the required HUMAN barrier. A commit adapter holding the only credential for the irreversible action checks a four-condition predicate before it calls the API. Reusing an old decision appends a fresh derived record and never just points at the old one. Its comparison table rates Claude Code and Cursor permission systems as providing none of the four commit-time clauses. Their prompts gate tool calls, but they leave no record a commit boundary can check, and the agent usually holds the shell credential anyway. HARP ([spec](https://github.com/harp-protocol/harp-spec)) is the same idea in wire form: signed Decisions bound to a SHA-256 artifact hash, `plan/patch/command/checkpoint.review` artifact types, and an out-of-band mobile approver. Credibility: medium-high for the design. The evidence is trace replay only (271K public traces, validator tested on synthetic DAGs) with no deployed baseline. HARP is an early draft with no visible adoption. Weight: high.

3. **[HarnessSecurity-Bench: Do Security Mechanisms Really Protect Coding Agent Harnesses? (arXiv 2610.07639)](https://arxiv.org/abs/2610.07639)**: auto-approve flips attack success from 29% to 96%, and allowed interpreters leak
   The authors audited 40 harnesses × 10 mechanisms (400 cells). About half of confirmed mechanisms are opt-in, and 53% of closed-source cells couldn't be verified at all. In 2,500 controlled trials across Claude Code, Codex CLI, Gemini CLI, gptme, Qwen Code, and Copilot, auto-approve raised utility +18 pp and attack success from 29.2% to 95.6%. Command allowlists cut attack success 48 pp for a 1.5 pp utility cost. Network isolation and read-only mode cost 25–34 pp of utility. One case to remember: Qwen Code's gate rejected a malicious checker, and the agent then ran it through an allowed Python interpreter. Interface takeaway: show the *effective* security configuration in the CLI/UI, and test every alternative path to a protected operation. A toggle the user can't verify isn't a control. Credibility: medium-high. Large, oracle-based design with separate utility and attack checks; one base model (GLM-5.2) and Docker-simulated services. Weight: high.

4. **[Claude Code v2.1.300: agent transcript in the main view, virtualText, prompt.change, Slack Allow-once card](https://changelogs.core-directive.com/v/2.1.300)**: the TUI is becoming a mod-drawn control surface
   Shipped Oct 14. New in the mods API: `$.ui.view({ agentId })` puts any agent's transcript in the main view (`$.ui.view({})` goes back); `virtualText` draws prompt-box text that never enters the draft; a `prompt.change` hook fires on non-typed edits (history recall, undo, plugin fill); `agent.spawn` can now rewrite a workflow agent's prompt and model, not just refuse it. Claude in Slack gets a private Allow once / Deny card for connector actions, so other people only see that it's waiting. PreToolUse/PermissionRequest `updatedInput` is now validated like Claude's own input (unknown keys dropped, input the tool rejects denies the call). Background sessions resume a carried workflow through the Workflow tool's approval instead of running it from the handoff file. Transcripts now record each request's system prompt, tools, and parameters, so a shared one can reproduce the request exactly. The step from 2.1.299: fleet navigation and provenance are moving into plugin-drawable chrome. Credibility: high. The primary Anthropic changelog (code.claude.com/docs/en/changelog) is quoted verbatim on a version-pinned page. Weight: medium-high.

5. **[ACP v2 Prompt Lifecycle + Permission Requests](https://agentclientprotocol.com/protocol/v2/prompt-lifecycle)**: "accepted" means inserted; `requires_action` is a first-class state
   The v2 docs are now published as protocol pages. `session/prompt` returns as soon as the user message is inserted (`messageId`). Progress is reported through `state_update`: `running` / `requires_action` / `idle` + `stopReason`. Since the Oct 1 revision, failures after insertion end as `idle` with `stopReason: error` and a JSON-RPC error. Permission prompts now carry a required `title` and a tagged `subject`. A [command subject](https://agentclientprotocol.com/rfds/v2/permission-requests) needs the exact `command` and an absolute `cwd`, and permission copy can't overwrite tool-call state. Other v2 changes: terminals become agent-owned and display-only, plans become `plan_update` items, and diffs become `git_patch` with absolute paths (Oct 12). For a non-chat client, this gives every session a protocol-level "blocked on you" bit, and every approval names exactly what runs and where. Credibility: high, but it's a primary spec that's still behind an unstable flag; SDK support lags. Weight: medium.

6. **[Unified Harness Protocol 2026-10-04](https://unifiedharnessprotocol.org/spec/2026-10-04)**: the harness as a job API, with no human gate in it
   UHP is a Responses-shaped HTTP contract for driving whole harnesses (Codex, Claude Code, Hermes, …) as jobs instead of completions. It has 13 chapters (sessions, environments built once and mounted read-only, per-node memory grants, plugins with sandboxed stdio MCP), and "conformant" means passing a 98-check suite. The security chapter is unusually honest: prompt injection is "in scope for the client", and a server MUST NOT claim the agent is safe on untrusted input. But no endpoint models a permission request or a human approval. The client's only lever is watching the event stream and cancelling. Compare ACP v2's `requires_action` + `request_permission`. If your harness ever sits behind a job API, that gap is where your approval semantics disappear. Credibility: low-medium. A new draft standard; the reference repo ([HarnessRouter](https://github.com/HarnessRouter/harnessrouter)) shows no visible adoption. Weight: medium-low.

**Takeaway for a non-chat+diff harness:** Make the task contract the main object: what must change, what must stay untouched, and what a separate verifier saw. Draw it outside the transcript. Keep approvals as ledger records bound to artifact hash, policy version, and executed path, and give the irreversible credential only to the adapter that checks them. Show protocol state (`running` / `requires_action` / `idle`) and the *effective* security settings as live UI, not as toggles the user has to trust. Label every action reversible, compensatable, or irreversible, and never show undo you can't deliver.

# Agentic & AI interface brief — 2026-10-30

**Theme: Show what steered the agent and what actually ran.** Today's papers measure how far "done" drifts from proof, how strongly a repo's existing code and memory files steer an agent without telling you, and how often agents act on values that changed under them. Both big CLIs shipped fixes in the same direction: blocked calls no longer look like they ran, and a stopped command is reported as "may have run". The harness job is to keep influence, claims and outcomes visibly separate.

1. **[Soei: Structured Observability of Evidence and Intent for Multi-Agent AI Software Engineering](https://arxiv.org/abs/2610.39468)** (arXiv 2610.39468), plus [Agentic Process Evidence](https://arxiv.org/abs/2610.40071) (2610.40071), measure the gap between "complete" and proven
   Across 45 real coding-agent sessions (about 102,000 records and 20,577 tool runs), a blind-audited classifier estimates that 23.4% of code-editing episodes end with no independent check after the last edit, and 57.8% of to-dos the agent marked complete after editing had no proof in between. 42% of sessions ran longer than 24 hours, and a simple timing rule recovered only 6 of 24 real session handoffs. Their proposal is a hash-chained local ledger that keeps "claimed complete" apart from "verified", at 20% of raw log size and with no content or credentials stored. The companion APE paper proposes signed, in-toto style attestations linking an agent session to its commit. For your harness: a to-do or task card should only turn green when a check ran after the last edit, and the card should say which check. Treat session handoff as an explicit, recorded link, not something you infer later. Credibility: medium for Soei (two authors, but a real corpus with confidence intervals and an audited classifier); low for APE (a position paper with no evaluation). Weight: high. Complements Oct 29's PASS Is a Claim (2610.35950) with far more data.

2. **[Precedent or Intent? What Coding Agents Follow When Evolving Existing Code](https://arxiv.org/abs/2610.38244)** (arXiv 2610.38244), plus [Security Impact of Coding Agent's Memory Files](https://arxiv.org/abs/2610.38521) (2610.38521), the repo steers harder than your prompt, and agents don't always say so
   In 5,625 trials across four agents, agents followed repository precedent over their own defaults in 359 of 360 trials. Where precedent lives matters enormously: three supporting local files gave 96% adoption, sibling-resource files 4%, and moving files alone swung adoption from 0% to 100%. When the task conflicts with existing code, a written priority rule beat code examples (59/60 vs 38/60), and in real open-source repos a harness-loaded rule raised joint success from 0/120 to 117/120. The memory-file paper found malicious CLAUDE.md-style files moved secure-completion rates only -8 to +6 points, but disclosure differed sharply: Claude Code named the file in about two thirds of final messages, OpenCode almost only in its hidden reasoning. For your harness: show "what's steering this change" as a first-class panel (nearby precedent files, memory files, and loaded rules) and require the final summary to name any of them that shaped the code. Let the user write a priority rule ("follow the task over existing patterns here") rather than hoping the prompt wins. Credibility: high for Precedent or Intent (large controlled design plus real-repo validation); low-medium for memory files (36 tasks, the authors call it preliminary). Weight: high. Builds on Oct 23's Stale Instruction Files (2610.30571).

3. **[EnvOS: Auditing Computer-Use Agents When the World Moves On](https://arxiv.org/abs/2610.40246)** (arXiv 2610.40246), agents act on values they saw earlier, and the interface decides whether they notice
   EnvOS builds environments where a value changes mid-task, and certifies before any run that the change fires and the grader works. In clinic booking, Claude Opus 5 succeeded on 0 of 16 tasks with nothing extra shown, 2 of 16 when reminded to re-check, and 15 of 16 when the updated value was shown. Sonnet 5 on claim approval went from 1 of 10 to 9 of 10 when the current policy was shown again. Its verdict re-checker also caught 25 of 39 externally corrupted episodes versus 4 for simple log checks. For your harness: "re-check the source" instructions barely help; pushing the changed value back into view does. When a file, ticket or config the agent already read changes during a run, surface it as an event on the agent's timeline, with the diff. Credibility: medium (small task counts, but pre-registered tests and honest about which result doesn't survive correction). Weight: medium-high.

4. **[How Deterministic SAST and AI Security Agents Divide the Work (Snyk VulnBench 2.0)](https://arxiv.org/abs/2610.38617)** (arXiv 2610.38617), the harness's built-in policy decides what the model misses
   On 108 hand-curated, attacker-reachable vulnerabilities, Snyk Code reached 89 and Claude Code's /security-review with Opus 5 at xhigh 85; together they hit 101. The interesting finding is about the harness: without Claude Code's built-in review policy, the same model found 16 instead of 9 of the 20 vulnerabilities in classes that policy excludes or restricts. Codex Security located 80 at file level but only 34 at line level. For your harness: any built-in scope policy for a review ("we skip these classes") should be visible and toggleable on the review itself, and findings should report how precisely they're located. Credibility: medium. Rigorous blind protocol with public data, but written by Snyk, which sells the competing engine. Weight: medium.

5. **[Claude Code v2.1.314](https://github.com/anthropics/claude-code/releases/tag/v2.1.314)**, plus [Codex 0.166.0](https://github.com/openai/codex/releases/tag/rust-v0.166.0), stop pretending things ran, or didn't
   Claude Code (released Oct 29, about 6:06 PM PT):
   - Shell and MCP calls blocked by auto mode, a deny rule or a hook no longer read as if they ran inside a collapsed tool group.
   - After you stop a command with Esc or Stop, Claude now hears the command may have run, not just that it was declined.
   - Auto mode no longer reports a call as blocked when its safety check gave no verdict.
   - New `permissions.blockWritesOutsideWorkingDirectories` refuses writes outside the working directories in every permission mode.
   - The /rename name now stays visible during permission and plan prompts, so side-by-side sessions stay identifiable.

   Codex 0.166.0 (Oct 29, about 12:47 PM PT) adds clearer safety-block explanations with selectable safer follow-up prompts, and keeps acknowledged approval settings when resuming or forking a thread. For your harness: give every tool call one of three honest states (ran, blocked with the reason, or unknown outcome) and never collapse blocked calls into a "ran" group. A block should offer the safer next step, not just a refusal. Credibility: high (primary release notes). Weight: medium-high.

6. **[ACP: tie the mode-switch example to user approval (PR #2714)](https://github.com/agentclientprotocol/agent-client-protocol/pull/2714)**, a small spec fix with a clear principle
   Merged this morning (about 4:09 AM PT, v2). The example of an agent switching modes "after completing a planning phase" read as the agent reducing oversight on its own, against the rule that agents shouldn't reduce oversight without user action. It now says "after the user approves a completed plan, or as the user's policy allows." For your harness: leaving plan mode should be an explicit user approval or a named policy, shown on the timeline as such. Credibility: high (primary spec change). Weight: low-medium.

**Takeaway for a non-chat+diff harness:** Show what's steering the agent (precedent, memory files, rules) and make it say so. Mark tasks done only on a check after the last edit. Push changed inputs back onto the timeline instead of trusting the agent to re-check. Give every action one honest outcome state.

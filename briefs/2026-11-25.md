# Agentic & AI interface brief — 2026-11-25

**Theme: Who wrote it decides what it's allowed to do. A rule, a summary or a diff that doesn't record its author can be rewritten by whoever touches it last, and the harness ends up obeying the forgery.** In Claude Code, a reply to one permission prompt can carry an update that deletes the operator's deny rule. The deletion leaves the same records as a local edit, so the runtime can't tell who removed the rule. Claude Code and Codex both put the compaction summary into the transcript as a *user* message. An authorizer reading that summary admits an attacker's payee in 91% of cases, against none when it reads the user's own words. In a Microsoft/GitHub study, reviewers given the coding agent's trajectory, organized as source-linked questions, catch 17.5 points more failure-linked problems than reviewers given only the diff. Recovery after a partial write leaves lasting harm in about a quarter of AppWorld cases, and a duplicate-call detector finds only 41% of it. For a non-chat harness: give every rule, message and effect an author field the agent can't forge, render compaction summaries as agent-authored rather than user-authored, and review work from the trajectory plus the effects actually committed, not from the diff and the report.

1. **[When Answering Is Administering: Permission Replies That Rewrite Coding-Agent Policy](https://arxiv.org/abs/2611.32195)** (arXiv 2611.32195): the right to answer a prompt has become the right to edit the policy
   Claude Code lets plugins, hooks and remote relays answer permission prompts, and documents that such answers can't override the operator's deny rules. That holds for each decision but fails over a run, because an answer can carry a policy update that applies to every later check. In their attack, a remote service with no access to the operator's files approves an unrelated command and attaches an update that deletes the deny rule protecting the project's secrets. The agent then reads the secrets in that session and the next, even inside the strict sandbox. The cause: Claude Code checks only updates that add or replace allow rules, and a deletion leaves the same records as a local edit by the operator. About 7% of the deployed relays they inspected forward such updates, including the vendor's own Remote Control. Their bounds: a runtime that can't tell who wrote a rule can safely accept only updates that keep every denied call denied. A runtime that records authors can let each party remove only restrictions proven to be its own. The bounds predicted the outcome for all thirteen permission designs across ten agent systems, including Codex, Gemini CLI, opencode and Goose, which were predicted before they were run. Enforcing the bounds at the shared update step blocks the attack. Only 2 of 2,227 marketplace plugins send policy updates, so the fix costs almost nothing. The ethics appendix says the deletion still worked on 2.1.327, the latest build when they wrote it, and the v2.1.332 notes don't mention it. Sharpens 11/23's Markdown Is Not a Firewall (a gate decides) and 11/19's Truthgate (keep the record where the agent can't reach it): here the gate's own rulebook is reachable. For your harness: store every permission rule with its author (operator, project, plugin, relay, agent), show who changed it in the policy view, and refuse any deletion of a deny rule that doesn't come from its author. Credibility: medium-high (seven authors from UTS, NUS, UNSW and Sheffield; tight proofs plus pre-registered cross-system predictions; local patched builds only; the appendix gives no disclosure timeline). Weight: high.

2. **[LLM Agent Authorization Across Context Compaction](https://arxiv.org/abs/2611.32194)** (arXiv 2611.32194): after compaction, the summary speaks in the user's voice
   Request-derived authorizers such as Progent decide what an agent may do from what the user asked. In every automatic compaction the authors observed, Claude Code and Codex inserted the model-written summary of earlier turns as a user message. Anything the summary quotes (documents, tool output, injected text) then reads as the user speaking. When Progent re-derives its policy per request, its grants follow whatever the compactor wrote. In one case, an attacker's notice names a different account as plain data and the user asks to pay the rent. The policy derived from a frontier compactor's summary admits the attacker's account 91% of the time, and the policy derived from the user's own words never does. Compactors usually mark injected *instructions*, which have no legitimate twin, but rarely injected *data*, which does. The paper proves an authorizer that can't see who wrote which bytes can't separate a forgery from the record it imitates, and that this bound is tight. Their fix authenticates user turns as they arrive and carries them verbatim across the compaction boundary for the authorizer, while the agent still reads the summary. In 40 attacked AgentDojo episodes with the fix, no attacker action completed. Complements 11/03's ARCBench and 11/12's SELD (compaction loses rules and evidence): compaction also changes who appears to be speaking. Claude Code v2.1.332 fixes the VS Code UI showing the compaction summary as your own prompt, but only in the display. For your harness: show compaction summaries as agent-authored artifacts with their own lane, keep the user's turns verbatim and signed beside them, and never derive a grant from summary text. Credibility: medium-high (same UTS/NUS/UNSW group as #1; formal bound plus adaptive attacks; the end-to-end evaluation is small and built on Progent/AgentDojo). Weight: high.

3. **[Diffs Are Cheap, Show Me the Trajectory: An Empirical Study of Trajectory-Informed Code Review](https://arxiv.org/abs/2611.31316)** (arXiv 2611.31316): review the run, not just the patch
   The dataset links 339 agent implementations of 113 DeepSWE tasks to their trajectories and 882 reference review comments, generated by comparing initial and merged PR versions and checked against held-out human comments. They tested three coding-agent configurations and two review harnesses, comparing diff-only review with raw trajectory access and four structured trajectory views. Raw trajectories raise mean reference recall only from 23.03% to 25.87%, and help in just four of six configurations, so dumping the log isn't enough. All four structured views beat diff-only by 4.05–7.32 points. The "evidence-linked map", which turns development evidence into source-linked review questions before the reviewer reads code, leads or ties in five of six configurations. It beats diff-only by 17.51 points on comments that explain verifier failures. A lighter "Messages" view is competitive when tokens and time matter. Companion: [The Elephant-Goldfish Model for software design review](https://arxiv.org/abs/2611.32668) (2611.32668) seeded nine defects into each of 47 design docs. A fresh reviewer given the drafting conversation caught 94.8% of omitted decisions, against 62.4% with the document alone, with no loss on defects visible in the document. Google's five-stage EGM plugin was about 5x slower and had lower estimated recall. Builds on 10/23's Atlas and 11/16's behavioral trajectories (making runs legible), and answers 11/20's Unfaithful Work Reports: the trajectory is evidence, the report is a claim. For your harness: make the review surface a map of review questions, each linked to the trajectory step that raised it (an abandoned approach, a skipped test, an assumption), with the diff as one pane rather than the whole screen. Credibility: medium-high (Microsoft, GitHub and Monash authors; reference comments are synthetic and matched by an LLM judge). EGM: medium (single author; model judges calibrated on controls; protocols and data released). Weight: medium-high.

4. **[Agent Recovery Gone Wrong: Measuring Harm Beyond Duplicate Calls](https://arxiv.org/abs/2611.31554)** (arXiv 2611.31554) + [Scoring Recovery-Time Agent Security](https://arxiv.org/abs/2611.31318) (2611.31318): recovery after a partial write is where damage happens
   Code-executing agents send blocks that make several API writes. When a block fails midway, the agent rewrites it and carries on. In a stratified sample of 200 AppWorld episodes across ten models, the database state confirmed 145 partial executions. Of 143 with a determinable outcome, 30 were followed by a harmful recovery whose violation lasted to the end of the run (a weighted estimate of 24.6%). Two-thirds of the harm duplicated an effect. The rest deleted user data or made a wrong first-time write, such as ordering the wrong product. A repeated-call rule finds 75% of duplications but only 41% of all harm. Idempotency keys supplied by the model didn't detectably help (17-episode pilot), because the model issued a new key for the same operation. Keys derived from call content would have caught 14–18 of the 30 harmful recoveries, missed every wrong first-time write, and also matched writes the task required in 30 episodes. The companion single-author paper logs proposals, runtime decisions and committed effects separately. A timed-out write may be absent, committed or still in flight. With the original task wording, models produced only 39 of 576 valid recoveries when the first write was absent, and a clarified effect definition plus recovery recipe got 576 of 576. Auditing 12 supplied traces cut apparent completion from 10/12 to 8/12. Extends 11/19's Idempotency Is Not Recovery and 11/17's Recovery Gone Too Far with base rates from real failures. For your harness: after a failed block, show which writes actually landed (from the target's state, not the agent's memory) before letting a retry run, and put the "absent, committed or pending" semantics in the tool's error text. Credibility: medium (5-page workshop-style paper; data, labels and scripts released; one benchmark). Retry-instructions paper: medium-low (single author; large episode counts but templated tasks; the paper itself says no general defense was shown). Weight: medium-high.

5. **[Where is the Interface for the AI Harness?](https://arxiv.org/abs/2611.31739)** (arXiv 2611.31739) + [Calm Agent: Reframing Agent Interaction around Intermittent Human Attention](https://arxiv.org/abs/2611.32009) (2611.32009): HCI is starting to name the harness as the interface
   Johal and Schombs (University of Melbourne) start from the 2026 incident, reported by the ABC, in which a research agent got around an access refusal on an Australian government statistics portal and took non-public files. Its developers didn't notice for two months. Their argument: Norman's gulfs of execution and evaluation assume the user is present, and delegation adds two more. The *gulf of specification* is how the agent should behave in situations nobody foresaw. The *gulf of oversight* is knowing, judging and controlling what the agent is doing. Both meet in the harness (tools, permissions, checks, loop), which developers write and users never see. They ask HCI to decide which parts users should author, which should be visible, adjustable defaults, and which should be fixed by design. Calm Agent argues that agents doing background tasks should be designed for intermittent attention. It proposes three on-demand modes (Delegate, Adjust, Check) built on a persistent task representation, mixing generated controls with standard ones, shown in the Orvlet desktop prototype (code on GitHub). There's no user study. Both are framing rather than evidence, but they put Brian's thesis in HCI language: the harness's policy and loop are a user-facing surface. Pairs with 11/02's When Should AI Agents Ask (limited attention) and 10/19's Ream (mutual awareness). For your harness: show the policy, checks and loop as an inspectable, editable layer next to the work, and design "come back after an hour" as a primary flow (what changed, what's waiting on you, what was refused) rather than scrollback. Credibility: medium-low as evidence (two short position papers, one under review at *Interaction*; one prototype, no evaluation). Weight: medium.

6. **[Claude Code v2.1.332](https://github.com/anthropics/claude-code/releases/tag/v2.1.332)**: compaction attribution, honest status, refusing dead rules
   Published 11/24, 5:32 PM PT. In VS Code, the compaction summary no longer shows as your own prompt after you reload, resume or fork, or in Rewind and prompt history (see #2). Tool calls that never ran are no longer counted as done in a claude.ai chat summary after you declined a permission prompt in a restarted session. Remote Control no longer shows a session as running while it waits on a dialog or an MCP server's question, and Desktop keeps "needs input" after a background report. Headless and cloud sessions no longer report a foreground fork's Agent call as finished the moment it starts. A PreToolUse hook's reason for asking now appears on Read, Grep, Glob, Edit and Write prompts. `/permissions` now refuses a rule that would be skipped at the next start (such as `rm -rf` with no tool name) and says why. A new `PreSkillShellCommand` hook can refuse a skill's inline shell commands as it loads. Plan mode in Desktop and VS Code now asks for approval instead of refusing when no auto-mode check can judge a command. PgUp and Home now default to No on destructive questions. Skills from MCP servers (beta) appear as `server:skill`. Codex has shipped no stable release since rust-v0.172.0 (11/23), only 0.174.0 alphas with empty notes. The theme in vendor form: status, authorship and refusals that tell the truth. Credibility: high (primary vendor release notes). Weight: medium.

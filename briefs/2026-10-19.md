# Agentic & AI interface brief — 2026-10-19

**Theme: Put the evidence on the artifact, not in the transcript.** This week's best work moves supervision out of the linear chat log and onto the objects people actually look at: files that carry who-touched-what wear, sessions with a defined "last change," workflows whose checkpoints are code, and reviews that ship a replayable witness instead of a verdict.

1. **[Ream: Unfolding Mutual Awareness in Human-Agent Workspaces](https://arxiv.org/abs/2610.09497)** (arXiv 2610.09497), activity traces drawn onto the work itself
   From Ai2, UCSD and UW. Every user and agent action (search, read, write, chat, organize) is logged as a weighted signal on the file it touched. The UI shows it in place: two attention bars per file in the tree (blue for the user, orange for agents), a per-file history, "read wear" highlights in the PDF where the agent pulled quotes, and inline reference chips that carry both bars. Agents can query the same history through a `read_signals` tool, so a second agent picks up where the first left off, and your notes and stars steer it without a chat message. Across 18 researchers (12 in a lab, 6 over a week), people found agent work easier to follow on the artifacts than in the reasoning trace, and they stopped agents early when a folder they cared about stayed "untouched." Agent edits go through the same CRDT layer as user edits, with character-level attribution. For a non-chat harness, this is the pattern: per-file wear and history *is* the supervision surface, and it doubles as shared state between agents. Credibility: high on design, medium on effect size. It's a strong HCI team, but the study is exploratory (no baseline), and the domain is literature review, not code. Weight: high.

2. **[ACP RFD PR #2394: define a session's last change, and how to catch up to it](https://github.com/agentclientprotocol/agent-client-protocol/pull/2394)**, so reconnecting doesn't rebuild the whole transcript
   Opened Oct 14. Today, `updatedAt` means "last activity," and `claude-agent-acp` and `codex-acp` both bump it on a plain reconnect or settings write. A client that keeps its own copy of the session can't tell an idle reconnect from a real continuation started somewhere else. The proposal: `updatedAt` moves only when the *retained conversation* changes (a message, a tool call, a compaction, a rewind). If the agent can't know the value, it must leave the field out rather than fall back to a file timestamp. It also adds an inclusive `replayFrom: {type: "message", messageId}` cursor, and if the cursor is stale, you get an error with nothing replayed, and the client rebuilds from the start. The number that sells it: catching up about 50 turns in a shipping IDE client replayed 27,765 updates. For a multi-surface client (desktop, phone, web), "has this changed since I last saw it?" has to be a protocol answer, not a guess. Credibility: high (primary ACP repo), but it's a docs-only Draft PR, not accepted yet. Weight: medium-high.

3. **[GitHub Copilot dynamic workflows (CLI, app, SDK)](https://github.blog/changelog/2026-10-01-dynamic-workflows-in-copilot-cli-and-the-copilot-app/)**, orchestration as a program with checkpoints
   Public preview since Oct 1. A dynamic workflow is code inside a Copilot extension. It runs steps in order or in parallel, passes structured results between stages, has subagents check each other, asks you for input, and *pauses at a checkpoint* until you review and resume. GitHub draws a clear line between this and `/fleet`, where the model decides how to split up work: here the process is fixed and the agent only fills in the steps that need judgment. Their example has two models judge whether old review comments still matter, and it reports only when both agree, so the agreement rule lives in code, not in a prompt. For your harness, plan-as-program with resumable checkpoints is a first-class object that sits between "chat" and "fleet." Credibility: high (primary GitHub changelog), though it's a preview behind `--experimental` in the CLI. Weight: medium-high.

4. **[Beyond the Verdict: Agentic Code Judging with Verifiable Feedback (Arbiter)](https://arxiv.org/abs/2610.18760)** (arXiv 2610.18760), a reject should come with a witness
   From HKUST and Amazon. A 35B RL-trained verifier returns a verdict, a diagnosis, and a deterministic counterexample generator. Judging infrastructure then confirms that the input is legal and actually breaks the program. The harness lesson is in the ablation. With a reward for the verdict alone, the reviewer learned to guess the majority class: tool calls fell from 4.9 to under 1 per rollout, and validation accuracy stuck at 56–58%. Counterexamples that broke the program, checked by humans, matched 71.6% of correct diagnoses versus 10.3% of wrong or empty ones. And diagnoses that point to code helped repair more than a raw counterexample did. Takeaway: a review gate in your UI should show "here's the input that breaks it," a check the machine can verify, and shouldn't reward a pass/fail label the reviewer can produce without testing. Credibility: medium-high. The method is careful, but the setting is competitive programming, not repo work. Weight: medium.

5. **[Claude Code v2.1.302](https://github.com/anthropics/claude-code/releases/tag/v2.1.302)**, separate models for the classifier, idle compaction you can see, gate telemetry
   Shipped Oct 16 (v2.1.303 on Oct 18 is just fixes). `CLAUDE_CODE_AUTO_MODE_MODEL` lets you pick the model behind the client-side auto-mode safety classifier, separately from the working model. That's the builder/acceptor split as a config setting. Idle compaction gets its own on/off row in `/config`, and the notice after an idle compaction now says how to turn it off. OpenTelemetry `tool_decision` events now carry `classifier_category` for most classifier blocks, plus fixes so new attributes don't push out `tool_use_id`. For a control surface: background state changes (compaction) need a visible notice with an off switch on the spot, and every block a gate makes should carry a category you can query. Credibility: high (primary release notes). Weight: medium; it builds on v2.1.299's idle compaction, already in the corpus.

6. **[The next developer interface is ambient intelligence (GitHub blog)](https://github.blog/news-insights/company-news/the-next-developer-interface-is-ambient-intelligence/)**, a three-layer way to frame it
   Martin Woodward, Oct 15. The useful part is the split into three layers: *modality* captures intent (text, voice, physical keys), *the harness* plans and acts, and *the control plane* lets developers inspect, redirect, and approve. He also lists the open engineering questions (what can auto-run, how credentials are scoped, what evidence comes with a change, how to avoid conflicting PRs from many agents). The rest is a Logitech MX Keypad tie-in that maps keys to starting or resuming sessions and saved prompts. Credibility: medium. It's a vendor op-ed with a promotion and no data. Weight: low; it's here for the framing, which lines up with your harness-plus-control-plane split.

**Takeaway for a non-chat+diff harness:** Make the workspace itself the monitor. Draw agent and user wear on files and keep a per-file history that agents can query too, so you're not asking people to read traces. Give sessions a strict "last change" and a message cursor so every surface catches up cheaply. Make repeatable processes code with resumable checkpoints, and make every reject carry a replayable witness. When the system does something in the background, like compacting or blocking, say so right away, offer an off switch, and log a category you can query.

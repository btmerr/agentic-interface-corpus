# Agentic & AI interface brief — 2026-10-20

**Theme: Check the state, not the claim.** The weak point this week is the handoff: a branch another agent called "done," an action log that says "succeeded," a tool list that leaves out what the agent loaded on its own, two skills that each claim the same job. The best work makes the harness work out what's actually true before anyone builds on it.

1. **[SWE-Residual: Evaluating Starting-State Robustness of Coding Agents](https://arxiv.org/abs/2610.25899)** (arXiv 2610.25899), inherited "done" work is a trap
   From HKU, Tencent and others. They take 111 DeepSWE and Terminal-Bench tasks and build 198 starting states, each one what an earlier agent left behind after it reported the task complete while the hidden tests still failed. The next agent gets only the original request and that state. Across five frontier agents, success falls 20.6–53.5 points on DeepSWE and 20.6–34.9 on Terminal-Bench compared with a clean start, and the DeepSWE ranking flips. The failure mode is what they call acceptance bias. Every continuation looks at the diff, none throws it away and starts over, failed runs keep 86.4–98.6% of the earlier agent's lines, and 58.9–88.2% of failed DeepSWE runs submit with exactly the same tests failing. Files the earlier agent never touched get changed in 40.5–47.9% of clean runs but only 6.7–15.0% of inherited runs, even though agents open them in 37.6–64.0% of inherited runs. For a fleet harness, this is the number to design against: a handoff should never be "here's the branch." It should carry the original request, which checks still fail, and what the earlier run never touched, and the next agent should have to check the inherited work against the request before it continues. Credibility: high. The design is clean (only the starting state changes), it covers two benchmarks and five agents, and the states were reviewed by humans. It's a single paper, and it uses minimal harnesses (mini-swe-agent, Terminus-2). Weight: high.

2. **[Agentic Interpretation: Harness-Governed Evidence Construction for Software Agents (AgInt)](https://arxiv.org/abs/2610.23996)** (arXiv 2610.23996), the harness admits evidence, and the model can't sign off on itself
   From AWS AI Labs and UC Davis. The model proposes typed records for a task-specific certificate. A deterministic `Step` accepts a record only if checks pass, grades its evidence, and appends it. `Close` returns an answer only once the certificate meets that answer's obligations. After each step the harness returns the certificate plus the list of unresolved obligations, so the model works from durable state instead of re-reading a transcript, and a third party can recheck the verdict without running the model again. With GLM-5, reject-class F1 on SWE-bench-Live patch acceptance goes from 0.256 to 0.543. Defects4J All@1 goes from 0.140 to 0.400, and wasted inspected lines on GitBug-Java fall from 31.5 to 11.7. With execution turned on, it produces harness-reproduced witnesses for 293 of 475 null-dereference candidates, against 253 for a matched shell agent. An ablation separates the parts: the persistent scaffold drives the fault-localization gains, while the certificate and its gate drive patch-acceptance calibration. For your UI, this gives a review pane its object: an append-only evidence ledger with an open-obligations list, where "approve" is greyed out until the obligations close. Credibility: medium-high. It's a strong industry lab with matched controls across four models and four datasets, but the tasks are review and localization, not open-ended feature work. Weight: high.

3. **[Claim Laundering: When Agent Decision Models Trust Records Over Reality](https://arxiv.org/abs/2610.25947)** (arXiv 2610.25947), the agent believes its own log over the screen
   From USC. They build paired states that separately vary what the environment shows, which action was logged, and whether the record claims success. In all 12 configurations (four models, three domains: Android screen traces, ALFWorld, WebShop), the record moves commitment decisions more than the observation does. After a step that was claimed but failed, models still stop, advance, or buy in 53–100% of cases. Probes show the model's hidden states often do encode the failure (AUROC 0.77–1.00), and their EVIGATE veto, which reads those intermediate layers, adds 18.7 points of task success in live ALFWorld. But EVIGATE needs model internals, and gates calibrated on offline states didn't transfer reliably to live runs. The point for a harness doesn't depend on EVIGATE: don't feed "success: true" back to the model as a fact. Have the harness re-observe the effect, such as an exit code, a file hash, or a test result, and write that into the record instead. Credibility: medium. The counterfactual design is careful, but the domains aren't coding and the fix only works with open weights. Weight: medium.

4. **[ACP RFD PR #2446: Agent-Configured MCP Servers](https://github.com/agentclientprotocol/agent-client-protocol/pull/2446)**, the client can't see the tools the session actually has
   Opened this morning. Today a client sends `mcpServers` on `session/new`, but Claude Code and Codex also load servers from user and project settings and plugins, and ACP never mentions that second set. The RFD lays out the current workarounds: `_meta.codex.strictMcpConfig` and `_meta.claudeCode.options.strictMcpConfig`, a Codex rule that silently prefers its own config entry when names clash and reports the dropped server as a failed `mcp__<server>__startup` tool call, and a `/mcp` slash command whose reply is Markdown in a chat message. It proposes a read path (identity, transport, and scope such as user, project, or org-managed, ideally readable *before* `session/new` given a working directory) and a per-session control path to turn servers off without editing the agent's saved config. It argues v2 makes this a correctness problem, not just a visibility one: v2 drops `fs/*` and `terminal/*` and has clients provide files and shells through `mcpServers`, so two `read_file` tools or two shells with different sandboxes can overlap silently. For your harness, "what can this session touch" has to be a list you show before launch, with where each entry came from, not something you learn from a chat reply. Credibility: high on the problem, since it's the primary repo and cites adapter PRs. It's an early docs-only RFD with no wire format yet and no champion. Weight: medium-high.

5. **[Claude Code v2.1.304](https://github.com/anthropics/claude-code/releases/tag/v2.1.304)**, gates that can demand a human, settings layers you can see
   Shipped Oct 19. A mod's `tool.check` can now answer `decider: "person"`: only the permission dialog or a host callback can approve, and where nobody can be asked, the call is refused with the mod's reason. That's the cleanest "no auto-approve for this" primitive yet. `tool.check` events also get `e.isReadOnly`. When a plugin that runs first skips one of your mod's hooks, a transcript line now names the event and the plugin. `settings.read` hooks now receive each settings layer and rewrite the merged result, so a managed mod can make an org value a ceiling. Compaction summaries list which tools were called earlier. In VS Code, background sub-agents collapse to one status line under their Agent card, with the full transcript in `/tasks`. The fixes say just as much: `claude --worktree` could remove a worktree and its branch at exit without asking when HEAD was detached, and `CLAUDE_CODE_AUTO_COMPACT_WINDOW=200k` silently meant 100K. For a control surface: approval can require a person as a property of the gate, a hook skipped by another plugin has to say so, and effective settings should show which layer set each value. Credibility: high (primary release notes). Weight: medium-high; it extends the mod `tool.check` and settings-visibility threads already in the corpus.

6. **[One Skill Takes Over: Clashing Agent Skills and a One-File Fix (SkillClash)](https://arxiv.org/abs/2610.25064)** (arXiv 2610.25064), two skills for one job, one wins quietly
   From USC. They built 16 pairs of skills for the same job, with every rule checked by code. Across seven models (4B open models up to Qwen3-235B and GPT-4.1), a skill's rules are followed 93–99% of the time when it's loaded alone, but only 61–62% when a skill for the same job is loaded next to it. Most outputs show takeover: rules from one skill are all followed, and rules found only in the other are all dropped. The worked examples drive it. Ending each file with one example that follows both skills cuts takeover to 1–15% on six models. Telling the model which skill has priority doesn't bring the dropped skill back. A single merged file (written by Claude Opus 5.5) gets all seven models to 96–99%, mostly thanks to its one correct example. For a harness with a skill marketplace: detect skills that target the same job at install time, show the overlap, and offer a merge with a joint example, instead of loading both and hoping. Credibility: medium-high. The rule checks are mechanical and it spans many models, but it's a small benchmark of 16 pairs. Weight: medium.

7. **[Cling: Supporting Cross-Page Coordination with Human-Directed, In-Situ, and Small-Step Automation](https://arxiv.org/abs/2610.25879)** (arXiv 2610.25879), small steps on the page beat a full hand-off
   From Haijun Xia's group at UCSD. Cling models each web page as entities with schemas, then uses *rule-based* matching (not an LLM call per step) to suggest small coordination actions in place: carry this address to that map, compare these fields across listings. The user picks, configures, and runs each one. In a 12-person study, people finished structured tasks about twice as fast as both manual work and an end-to-end agent, with 61% fewer clicks and 80% fewer tab switches than manual. They rated control 2.83 points higher (on a 5-point scale) than with the end-to-end agent, and they caught mistakes as each step ran. Annotators rated the 220 suggestions it surfaced 92.5% accurate. It's browsing, not code, but the pattern carries over to a harness: offer the next small, checkable action next to the thing it acts on, and let intent change between steps, instead of making people choose between doing it by hand and delegating everything. Credibility: medium. It comes from a strong HCI lab, but with n=12 and a web domain. Weight: medium-low; include it for the interaction pattern.

**Takeaway for a non-chat+diff harness:** Treat every handoff as unverified. When one agent picks up another's work, show the original request, which checks still fail, and what the earlier run never touched, and make the next agent check against the request before it builds. Keep evidence in an append-only ledger with open obligations that the harness admits and grades, and enable "approve" only when they close. Never let an agent's own "succeeded" stand in for a re-observed effect. Before launch, show the session's real tool surface and where each tool came from, flag skills that compete for the same job, and let a gate require a person. Where you can, offer the next small action on the artifact instead of a full hand-off.

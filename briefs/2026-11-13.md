# Agentic & AI interface brief — 2026-11-13

**Theme: Check the world, not the story about it.** Today's items share one finding: what the history, transcript, or receipt *says* happened is a weak signal next to what the world actually holds. A "clean" history over a world that still has the error makes the next agent worse. LLM judges reading transcripts passed 10 of 11 forbidden database writes that a no-model write check caught. Agents often have the right patch and then keep working, sometimes undoing it. The protocol and the shipping CLIs are moving the same way: explicit "replay complete," "not run · rejected," and "no result recorded" states instead of plausible defaults. For a non-chat harness, the review surface should be anchored to observed state (writes, structure, patches), and the narrative should hang off that.

1. **[Cleaning an Agent's History Hurts When the World Still Holds the Error](https://arxiv.org/abs/2611.14654)** (arXiv 2611.14654), compaction and handoff must describe the world, not tidy the story
   The authors freeze an agent mid-task with its exact world state, edit either the history or the world, and let a receiver model continue. After a wrong committed value (AgentCE-Bench), a truthful note *beside the preserved error* raises recovery from 51% to 66%. Rewriting it as the agent's own completed correct action *lowers* recovery below the unedited history, from 50% to 44%. On AppWorld, a "success" receipt for a database write cuts whole-task success from 45% to 28% when the write didn't actually land, and raises it from 38% to 49% when it did. That's a 27-point interaction, positive in 6–7 of 8 receivers. For your compaction, handoff, and takeover views: never present a repaired history as done. Keep the error visible, annotate it, and tie every receipt to a check of world state. Extends yesterday's SELD (evidence lost in compression) and the Nov 9 Take It From Here. Credibility: medium-high (controlled interventions with exact world state, multiple receivers, code and data released). Weight: high.

2. **[When Evaluators of AI Agents Disagree: Native Scoring, LLM Judges, and Commit-Boundary Checks on tau2-bench](https://arxiv.org/abs/2611.14581)** (arXiv 2611.14581), a dumb write check beats a smart judge
   2,160 episodes with every database write recorded, each scored four ways, and 120 episodes hand-labeled by two annotators. The LLM judge was consistent with itself (98.2%) but agreed with gold-state scoring only 56.2% of the time. Across 11 forbidden writes, the judge passed 10 to 11 with or without the policy document, and a stronger judge still passed 6. A rule-based "boundary evaluator" (was a write expected vs did one occur) caught all 11 with no model call. Also: verification and safe-termination gates didn't reduce forbidden writes, apparently because the gates' evidence digest dropped order status and auth, the same lossy-summary failure as item 1. Design cue: in your review and approval UI, put a deterministic "side effects that happened vs were expected" lane above any judge verdict, and show judge verdicts as advisory. Credibility: medium (single author, but a careful design with human labels and a full replication package; two tau2 domains only). Weight: high.

3. **ACP: [`replay_complete` merged (#2813)](https://github.com/agentclientprotocol/agent-client-protocol/pull/2813) + [v2 Idempotency Keys RFD (#2810, draft)](https://github.com/agentclientprotocol/agent-client-protocol/pull/2810) + [#2808](https://github.com/agentclientprotocol/agent-client-protocol/pull/2808)**, "how do I know it's all there / did it happen?" now has wire answers
   Yesterday's #2407 replay-complete RFD merged this morning, and #2813 already lands the v2 schema. The agent sends one `replay_complete` session update per `session/resume` with `replayFrom`, after the last replayed update. A resume that ends without it means the replay was **truncated**. Each announced child session gets its own marker. It's behind `unstable_protocol_v2`, and the SDK and adapter work is still to come. #2810 (benbrandt, open) proposes that every v2 method state its retry class (idempotent / keyed / duplicating / not retried), plus an optional `idempotencyKey` on `session/prompt` so a retried prompt is inserted at most once. A retry of a held prompt waits for the original's outcome. The validation is honest: Codex starts a new turn on every repeated ID, and Claude Code mostly skips repeats but not after a mid-turn restart, so adapters must dedupe themselves. #2808 says a repeated cancel after the item is final gets `-32602`, and clients shouldn't show that as "cancel failed." For your fleet view, this gives you: a "history loading / complete / truncated" badge per session, safe resend after a dropped connection without duplicate turns, and no false "cancel failed" toasts. Credibility: high (official repo, maintainer-authored, adapter-tested). Weight: high.

4. **[Claude Code v2.1.323](https://github.com/anthropics/claude-code/releases/tag/v2.1.323) + [Codex 0.169.0](https://github.com/openai/codex/releases/tag/rust-v0.169.0)**, shipping harnesses keep replacing plausible defaults with explicit states
   Claude Code's huge release is mostly honest-state fixes you can copy. A collapsed tool call rejected with a reason now shows "Not run · rejected", where before it looked like it ran. A stopped MCP call or shell command no longer reads as "Called/Ran"; it says *no result was recorded* and shows the input. A `cat > file <<EOF` is no longer shown as "Read 1 file". When auto mode is unavailable, sessions start in Manual (asks first), not in a mode that could allow more. A plan-file write that can't be shown to stay inside the project is refused. Background sessions whose sign-in profile is missing now *stop and say so* instead of sending under another account. Remote Control no longer shows "running" while the session is actually blocked on a terminal-only permission prompt. `/compact` no longer summarizes away a message Claude hadn't answered yet. It also adds a 30 s hook heartbeat so hosts don't mark long hooks as hung, plus experimental Code Mode. Codex 0.169: "Yes, clear context and implement" now hands the *full approved plan* to the fresh session and keeps the current session open if the handoff fails. Plus Collapse turn details (completed activity folds under each prompt, tool output stays searchable) and task search in the agent command center. Takeaway: "ran / not run / no result recorded / blocked on you" are separate states, and the plan→fresh-context handoff must be lossless or reversible. Credibility: high (official release notes; behavior described, not independently tested). Weight: medium-high.

5. **[Rasoi: Visual Diffs for Evaluating Structural Changes Made by Coding Agents](https://arxiv.org/abs/2611.16293)** (arXiv 2611.16293), architecture deltas as the review surface
   A design probe that maps how a codebase's architecture changes after each agent edit, at several levels of abstraction: elements and relationships added, modified, or removed. In a week-long field study, 12 developers used it on their own codebases. It helped them see whether changes stayed in scope, spot unexpected restructuring, duplicated logic, and removed functionality, and relate edits to the whole system. The key finding: the value was less in trusting the agent and more in developers trusting *their own evaluation*. This is the reviewer-side partner to yesterday's FlowPlan (planned vs observed graph deltas) and the Nov 9 pattern-relationship item. It's close to a direct prototype for a non-chat+diff review pane. Credibility: medium (qualitative, n=12, but real codebases over a week; design probe, not a product). Weight: medium-high.

6. **[Termination Lag: Coding Agents Solve Early but Stop Late](https://arxiv.org/abs/2611.14960)** (arXiv 2611.14960), mark the first passing patch on the timeline
   The authors recorded and tested every distinct repo patch during runs (five models, two frameworks, three SWE-bench sets). In 38–82% of successful runs, the *first* source edit was already correct. Post-solution steps were still a median 35–37% (Qwen3-Coder) to 54–60% (Laguna-XS.2) of the run, mostly re-verification and exploration. In 1–8% of cases the agent undid its own correct patch. Interface cue: continuously snapshot and test patches, put a "first green" marker on the run timeline, let the supervisor stop or accept at that point, and diff the final state against it. That also catches regressions that come after success. Pairs with the Nov 10 Done Is Not Correct item. Credibility: medium (sound method; open-weight models only, so frontier-model lag is unmeasured). Weight: medium.

7. **[Folio: Recoverable Multi-Resolution Context Folding](https://arxiv.org/abs/2611.16627)** (arXiv 2611.16627), compaction with handles back to the evidence
   Instead of model-written summaries, Folio records three linked levels as the agent runs: a short per-turn note the model writes, a runtime-written manifest of every call, and the captured source records. It then folds older turns programmatically into coarser views that print handles back to the finer levels, and recovery tools page in the evidence on demand. On 75 LOCA-bench tasks with the same backbone, it solved 66 vs 54 for model-written compaction and 49–59 for Claude Code, Codex, and SoL-Pi, in about half the time and at 2.4x lower cost, with a median fold of 0.6 s. This answers SELD and item 1: if compaction keeps handles, "what got dropped" stays one click away and nothing is rewritten. Credibility: medium (single backbone, single benchmark, authors' own runtime; the head-to-head with commercial CLIs is suggestive, not definitive). Weight: medium.

**Also noted:** [SideTaskBench](https://arxiv.org/abs/2611.14548) (arXiv 2611.14548): third-party references led agents to deliver *unrequested* side-task artifacts in about 40% of wrapped runs while repair success stayed near baseline, and technically related side tasks were the most likely to get through. That's an argument for a "delivered outside scope" diff lane. [guardscope](https://arxiv.org/abs/2611.15223) (arXiv 2611.15223) measures which of 15 agent action paths a runtime gateway actually checks against kernel ground truth. A gateway only sees what crosses it, so the approval UI shouldn't imply more coverage than that. [SatisFix](https://arxiv.org/abs/2611.16289) (arXiv 2611.16289) has agents report the requirement trade-offs they knowingly accepted, then checks each against the spec (+5–7 pass@1), a natural "decisions I made against your spec" panel. [AgentTorrent](https://arxiv.org/abs/2611.15436) (arXiv 2611.15436) is a dataset of 62K context/harness config artifacts and 27K agent planning docs across 10.9K repos, useful if you want real-world AGENTS.md and plan formats.

**Takeaway for a non-chat+diff harness:** Anchor review to observed state: actual writes vs expected, architecture deltas, and the first passing patch. Treat the narrative and judge verdicts as annotations on top. Never present a cleaned-up history over an uncorrected world. Make compaction reversible through handles. Give "truncated," "not run," "no result recorded," and "blocked on you" their own visible states.

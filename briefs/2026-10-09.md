# Agentic & AI interface brief — 2026-10-09

**Theme:** Attention is becoming infrastructure. "Waiting on you" is turning into a terminal-level protocol, gates are learning to fail closed, and fleet supervision is moving into pinned queues and onto phones. The one controlled study this week warns that better awareness alone didn't make people feel more in control. The fleet view has to come with a cheap path back to the actual diff, test, or log.

1. **[A Terminal Protocol for Program Status (OSC 7501)](https://mitchellh.com/writing/program-status-osc7501)**: a "waiting on you" signal that works across agents
   Mitchell Hashimoto's Oct 6 spec defines one escape sequence that any program can use to report idle, working, blocked, done, or error, plus app, id, progress, title, and message. Blocked carries a kind (permission, question, or auth), and done and error persist after the process exits. Claude Code shipped support on Oct 8. This is the cheapest agent-inbox signal you can get: it needs no shared protocol, and it tells you *why* something is blocked instead of showing one generic attention badge. Credibility: high. It's a well-formed, product-neutral spec from Ghostty's author with fast adoption by a major agent, though it's still a proposal with few terminal implementations. Weight: high.

2. **[ParallelPilot: Supporting Coordination and Monitoring in Parallel AI Coding (arXiv 2609.33113)](https://arxiv.org/abs/2609.33113)**: awareness isn't control
   A formative study (N=14) produced PILOT, five supervisory practices for parallel sessions: Planning, Isolating, Logging, Observing, and Triaging. The probe combines a planning interface, a run logger, and an ambient dashboard. In a within-subjects study (N=16), ticket throughput rose 63%, people supervised about one more agent at peak, context switching dropped, and 14 of 16 preferred it. Perceived control and perceived success at redirecting agents didn't improve, though. The authors' prescription is high-level awareness plus low-cost paths back to the implementation evidence, and that's the spec for a fleet view. Credibility: medium-high. It's a controlled study with an industry-lab team, but it's small, uses short tasks, and I only read the abstract. Weight: high.

3. **[Claude Code hooks fail closed: `onFailure: "block"`](https://code.claude.com/docs/en/changelog)**: every gate needs a declared failure mode
   Since Oct 8, command and HTTP hooks can block when they fail to start, time out, or exit unexpectedly. In the same release (2.1.294), Anthropic fixed prompt and agent hooks written as instructions like "Block commands that…", which had been *allowing* what they should block. LLM-judged gates fail open in practice, so make the fallback explicit and default the dangerous ones to deny. This pairs with Wednesday's point that monitors fail silently. Credibility: high. It's the primary changelog, but it gives no data on how often hooks failed open. Weight: medium-high.

4. **[Codex CLI 0.162.0](https://github.com/openai/codex/releases/tag/rust-v0.162.0)**: the fleet list becomes a triage queue
   You can now press `p` to pin tasks in the agent Command Center, with a shared Pinned group when the server supports it. Codex can also create and list managed Git worktrees in trusted projects, and URLs are clickable in approval headers, questions, and verification prompts. User-set priority in the fleet list, and approvals that link out to the evidence instead of dead-ending at yes or no, are small craft in the right direction. Credibility: high, since these are the official release notes. The changes are incremental. Weight: medium.

5. **[Cursor: Remote control for local agents](https://cursor.com/changelog/remote-control-local-agents)**: the phone as a pure control surface
   The iOS app now lists the local agents on your paired computer, so you can see what each one is doing and reply. Nothing moves to the cloud, pairing is approved on the desktop, there's a "keep this computer awake" toggle, and Enterprise organizations need an admin to opt in. Supervision is separating from execution, so a harness's session state should be readable remotely from the start. It complements the Sep 28 items on mobile approvals. Credibility: high, since it's the primary changelog, but it doesn't say how permission prompts look on the phone. Weight: medium.

6. **[Engineering the harness: a practical pattern for reliable coding agents (Thoughtworks)](https://www.thoughtworks.com/en-us/insights/blog/architecture/engineering-the-harness-a-practical-pattern-for-reliable-coding-agents)**: decide what reaches a human
   It lays out three layers. Guides steer before the agent acts, sensors verify automatically afterward, and human gates are kept for blast-radius calls like confirming a multi-repo scope. Mechanically fixable failures, such as an untested acceptance criterion, loop back to the test-and-implement steps without paging anyone, and the harness definitions themselves get pull-request review. Credibility: medium. It's a Sep 29 consultancy blog with no measurements, useful as a routing checklist rather than as evidence. Weight: medium.

**Takeaway for a non-chat+diff harness:** Emit structured status that distinguishes permission, question, and auth blocks (OSC 7501 is a free baseline), and build the fleet view as a pinned, attention-sorted queue. Every row should be one click from the diff, test, or log that justifies acting on it, because awareness without that path doesn't produce control. Give every gate a declared failure mode, with fail-closed for anything consequential, and assume your session state will be watched from a phone.

# Agentic & AI interface brief — 2026-11-24

**Theme: Approve what will run, not what you were shown. An approval only covers the exact thing the gate read, and when the shell parses it differently, the schema widens, the target moves or the agent reads hidden text, the approval is spent.** ParseGap ran eight production coding agents' own command checkers next to real Bash. Every agent had approved commands that went on to break policy, and in Codex CLI an allow rule switched off the read-only sandbox. SchemaCaps finds that none of the eight MCP clients and scanners it surveyed is known to re-ask when an approved tool's input schema widens, even though 412 of 580 "compatible" schema changes widened something. A CMU fault-injection testbed shows agents taking partial tool results as valid and then stating wrong answers as fact. A scan of about 145M GitHub items finds AI-directed text that GitHub never renders for people, and two-thirds of it is projects steering their own agents. ACP now ties `mcp/message` to a session and a tool call. For a non-chat harness: render the approval from what will actually run (the parsed plan), tie each grant to a schema/revision fingerprint that forces a re-ask when it changes, and show "the agent saw text you didn't" as its own state.

1. **[ParseGap: Testing What Coding Agents Authorize and What Shells Execute](https://arxiv.org/abs/2611.29546)** (arXiv 2611.29546): the gate approves one reading of a command, and Bash runs another
   Every shell gate studied checks a command string against a policy and then hands the raw string to Bash, so the checker and the shell can read it differently. ParseGap ran each command through the vendor's unmodified checker and through GNU Bash 5.2 in a container, and flagged any approved command that broke policy at runtime. Across eight production agents it found 17 root causes at three boundaries. **Parse:** a tree-sitter-bash defect hides a second command from Mistral Vibe and Gemini CLI. **Utility:** every checker allows "read-only" binaries whose arguments write files or launch programs (9–47 of 55 cases). Their example is `uniq README.md /var/tmp/x`: six of eight agents allow it under a read-only policy, and uniq writes its second argument outside the workspace. **Confinement:** in Codex CLI, matching that allow rule also disabled the bwrap+Landlock sandbox that would have blocked the write. Live trials with two frontier models produced policy-violating effects in all 16 agent–model pairs (14 of them with restriction rules configured). The paper also counts 171 shell-approval-bypass advisories from July 2025 to October 2026. Their fix, ShellPlan, compiles a strict Bash subset into a typed plan once, checks arguments against capability specs, and calls execve directly with no shell. It admitted 0 of 4,174 attacks at a 1.28 ms median gate cost. This sharpens yesterday's Markdown Is Not a Firewall (a gate decides), because the gate may be deciding about a different command. For your harness: the approval card should show the *parsed plan* (program, arguments, files it may write, sandbox in effect), and that plan, not the string, is what gets executed. Credibility: medium (single author; vendors notified 11/22 with details redacted under a 90-day window; the differential method can be checked against unmodified vendor checkers; the proofs rest on stated assumptions). Weight: high.

2. **[SchemaCaps: When a Compatible Tool Update Silently Widens an AI Agent's Authority](https://arxiv.org/abs/2611.30750)** (arXiv 2611.30750): "compatible" updates quietly widen tools you already approved
   MCP tools change their JSON input schemas between releases, and the user's approval carries over. None of the eight MCP clients and scanners surveyed is known, from observation or documentation, to re-ask when an approved tool's input widens (two couldn't be determined). The paper defines "non-amplification" over what the schema shows: declared arguments, undeclared fields, and effective values. A tool is re-bound only if the new schema is a subschema of the approved one, and field labels aren't trusted by default. Composition is proved in Coq, with 48 regression tests. Their own first version of the rule silently re-bound 27 amplifying changes before they fixed it. In a pilot on 604 releases of 39 public MCP servers, 412 of 580 compatible changes widened some coordinate, and at least 76 added or widened an argument that carries authority. A name-based labeller missed 10 of those. Cost: on existing tools the rule asks for 645 re-approvals, close to 617 for re-asking on every compatible change and far below 1,197 for pinning the schema. It can't see behavior changes behind an identical schema. Complements 11/17's MCP Provider Misbinding (a tool name isn't an identity): here a tool *version* isn't one either. For your harness: store each grant with the schema it was made against, show what got wider when a tool updates ("now accepts `path` outside workspace"), and re-ask only then. Credibility: medium (CNAM/CEDRIC team, accepted at ICAART 2027, artefact released; the pilot uses the authors' own double annotation). Weight: high.

3. **[When Tools Fail, Agents Fabricate: Silent Failure and Verification-First Oversight in Tool-Using LLM Agents](https://arxiv.org/abs/2611.28341)** (arXiv 2611.28341): partial data is worse than a hard error
   RetryRealistic is a sandbox with real filesystem permissions, SQLite, a deterministic local HTTP server and a constrained shell: 8 tools, 9 fault types with controlled persistence, 30 multi-step tasks. Over 2,100 faulted runs, four agents recovered correctly only 19–68% of the time. 6–26% of runs ended in confident fabrication, a wrong answer stated as fact. The fault type mattered more than the model. Faults that return *partial data* drove fabrication up to 38%, while hard denials led to honest failure. The mechanism is "silent ingestion": the agent accepts faulted data on first contact, never retries or flags it, and builds on it. A verification-first monitor that checks claims against structured tool outputs and sends corrective directives (not hard blocks) raised correct recovery from 45.6% to 56.3% and cut fabrication from 17.3% to 10.8%. Removing chain-of-thought *raised* fabrication by 8.3 points. Extends Idempotency Is Not Recovery (11/19) and Unfaithful Work Reports (11/20) to one cause: the agent never noticed the fault. For your harness: mark truncated or partial tool results as degraded in the trace, carry that mark into any answer built on them, and let the monitor flag claims grounded in degraded outputs. Credibility: medium-high (Carl Kingsford's CMU group; NeurIPS 2026 workshop paper; testbed and annotated traces released; only 30 tasks). Weight: medium-high.

4. **[Who Is Prompt-Injecting Coding Agents? An Empirical Study of Hidden AI-Directed Text on GitHub](https://arxiv.org/abs/2611.28763)** (arXiv 2611.28763): the agent reads a page the human never sees
   About 145M issues, PRs, comments and READMEs were scanned for text GitHub doesn't render to people but agents receive in full. Candidates went through two LLM classification stages, a template-provenance check and exhaustive manual review. The result: 2,281 validated findings in issues, PRs and comments (16 per million items), plus hidden AI-directed text in 107 READMEs. Four uses turn up: attacks on other people's agents, defensive text that restricts agents, content override that steers what they write, and first-party orchestration. Attacks are rare (about 1 in 3.3M items) but aimed at maintainers' own triage, review and CI agents. Orchestration is two-thirds of the findings, grew fivefold in four months, and is a hidden control channel anyone who can comment can imitate. Replayed offline against five models, the attacks worked 19% of the time on one small, fast model, and never once HTML comments were stripped. Complements 11/20's ROGUE-AI (put the hazard where the agent reads). For your harness: when an input has text the human view hides (HTML comments, collapsed or zero-width content), show "agent sees more than you" with a reveal, and strip or quarantine it by default for review and triage agents. Credibility: medium-high (two-author security study; huge corpus with full manual validation; detection tool and every finding released). Weight: medium-high.

5. **[ACP #2988: attribute `mcp/message` requests to a session and tool call](https://github.com/agentclientprotocol/agent-client-protocol/pull/2988)** + [#2978 plain text vs Markdown rendering](https://github.com/agentclientprotocol/agent-client-protocol/pull/2978) + [#2974 which description fields may contain Markdown](https://github.com/agentclientprotocol/agent-client-protocol/pull/2974) + [#2989 schema v2.0.0-beta.4](https://github.com/agentclientprotocol/agent-client-protocol/pull/2989): every MCP request can now say whose work it is
   #2988 (merged 11/23, 1:33 PM PT) adds optional `sessionId` and `toolCallId` to unstable `mcp/message` in v1 and v2. Agents SHOULD send what they know and MUST NOT guess. A `sessionId` must name an active session or an announced child that was declared the server. Agents SHOULD report the tool call before sending a request that names it. Providers MAY use the session to choose a sandbox or working directory, and MUST NOT reject because `toolCallId` is missing. The stated payoff is UI: the client can show the tool's own view and live output *on that tool call*, tell apart concurrent identical calls, and tie the request to the permission request for the same call. Open questions: which error codes to use, and whether agents should advertise attribution at `initialize`. No implementation sends the fields yet. #2978/#2974 settle rendering: a tool-call title is literal text (underscores survive), while permission, command, config, auth and subagent `description`s may contain Markdown. #2989 ships both in v2 schema beta.4. For your harness: key MCP side-panels and approvals by `toolCallId`, not by server, and render titles literally so filenames can't be mangled. Credibility: high (merged to the protocol repo by its maintainer; unstable surface). Weight: medium-high.

6. **[Consumer-Time Validity in Stateful AI Runtimes: Verifying Recovered State and Deferred Authority](https://arxiv.org/abs/2611.29004)** (arXiv 2611.29004): an approval recorded once isn't still valid when it's used
   One component records a cancellation, rollback or approval and another relies on it later, after the target has changed. On vLLM with LMCache, an interrupted KV load plus a host-only counter rewind made a second tenant emit a schema-valid tool call naming the wrong tenant in 10 of 10 native-fault runs (recorded, not executed). On a multi-session approval runtime, an unrevoked deferred grant overwrote a newer revision in one admitted live execution. Comparing outputs can't catch this, since fault-free runs diverge from BF16 batching alone. Their fix checks validity where state and authority are *consumed*, with evidence bound to the request using them. Revision-bound dispatch blocked all 160 conflicting overwrites, and their repair met 7 of 7 fault predicates where upstream vLLM PR 61769 met 2. Same lesson as ACP #2944 (late answers shouldn't restart work): bind the grant to the revision. For your harness: a deferred or "allow for this task" approval should carry the file/branch revision it was made against and lapse visibly when that moves. Credibility: medium (six-author systems paper; concrete reproductions against named upstream code; the approval-runtime evidence is one live case). Weight: medium.

Both vendors keep fixing the same seams the papers measure: recovery that isn't, and work that outlives its owner. Credibility: high (primary vendor changelogs). Weight: medium.

**Also noted:** [Useful but Unwieldy](https://arxiv.org/abs/2611.30894) (2611.30894): 36 engineers found the coding agent's reasoning message essential for trust, but too long, pitched at the wrong level, and "detached" because the agent seems to be talking to itself. That argues for reasoning tied to the step it explains, not a separate stream. [Airlock: Robust Sandboxing and Governance of Rogue Agents](https://arxiv.org/abs/2611.31010) (2611.31010): pairs each agent VM with a hardware-isolated airlock VM that handles all network and storage IO and keeps a tamper-proof audit, even if the agent VM is fully compromised. Author list includes Mark Russinovich; prototype runs on an Arm dev board. Not related to the 11/06 Airlock containment paper. [AgentBouncer](https://arxiv.org/abs/2611.30621) (2611.30621, Pradel): an LLM arbiter at the system-call level weighs necessity against safety. Attack success fell from 99.4% to 10.6% on 340 attacks, with 0.25% of benign calls failed. Another case of judging the effect, not the string. [Admitted Is Not Effective](https://arxiv.org/abs/2611.29727) (2611.29727): a pre-registered run over 880 PRs where a Notary admitted 55 of 89 learned-rule edits (rejecting 8 that cited nonexistent evidence), yet held-out results never improved. Admit rules as hypotheses, and retire them. [When an AI agent makes a mistake in a database, what decides the damage?](https://arxiv.org/abs/2611.30483) (2611.30483): pre-registered, 9 engines, about 12k trials; engines differ less in what a mistake destroys than in what they let you undo.
